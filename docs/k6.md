# Distributed k6

```
make k6-run TEST=load PARALLELISM=4
        │
        ▼
TestRun "load" (namespace loadtest) ──► k6-operator (control-plane node)
                                              │
                    ┌─────────────────────────┼──────────────────────────┐
                    ▼                         ▼                          ▼
             initializer pod         runner pods x4 (paused)        starter pod
          (k6 inspect: validates   load-1 .. load-4, each runs     (starts all runners
           script, reads options)  1/4 of the VUs                   at the same time)
                                              │
                    all on node worker2 (workload=loadgen)
                                              │
              HTTP ──► api-gateway.shop:8080  │  remote write ──► Prometheus ──► Grafana (Shop dashboard)
```

## Scripts

| File | Purpose |
|---|---|
| `k6/shop.js` | user flow: list products, create order, read order back |
| `k6/smoke.js` | 2 VUs, 30s, local run (`make smoke`) |
| `k6/load.js` | ramp to 40 VUs in 1m, hold 3m, ramp down 30s |

`make k6-scripts` uploads every file in `k6/` to the ConfigMap `k6-scripts`.
Scripts import each other with relative paths (`./shop.js`); ConfigMap keys are flat, so no subfolders.

## Running

```bash
make k6-operator                      # once
make k6-run TEST=load PARALLELISM=4   # uploads scripts, recreates the TestRun
make k6-logs TEST=load                # follow runner output
kubectl -n loadtest get testrun       # STAGE: initialization -> created -> started -> finished
```

`deploy/k6/testrun.yaml` is the template. `TESTID` becomes `<test>-<date>-<time>` and is added
to every k6 metric as the `testid` label.

## How VUs are split

k6-operator gives each runner an execution segment (`--execution-segment 0:1/4`, `1/4:2/4`, ...).
With `load.js` at 40 VUs and parallelism 4, each runner runs 10 VUs, following the same stages.

## Thresholds are per runner

Each runner evaluates thresholds on its own share of the traffic and prints its own summary.
There is no merged summary in the pod logs:

```
runner 1  create_order p(95)=34.62ms
runner 2  create_order p(95)=31.19ms
runner 3  create_order p(95)=35.67ms
runner 4  create_order p(95)=32.66ms
```

The global result comes from Prometheus.

## Metrics in Prometheus

Output `experimental-prometheus-rw` to `kps-kube-prometheus-stack-prometheus.monitoring:9090/api/v1/write`.

`K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true`: duration metrics are sent as native histograms
(full distribution) instead of precomputed p95 per runner. Percentiles from different runners
cannot be averaged; histograms can be summed, then a percentile is computed on the total.

| Metric | Type | Labels |
|---|---|---|
| `k6_vus` | gauge | `testid`, `instance_id` (runner) |
| `k6_http_reqs_total` | counter | `testid`, `name`, `method`, `status`, ... |
| `k6_http_req_duration_seconds` | native histogram | `testid`, `name`, ... |
| `k6_http_req_failed_rate` | gauge | `testid` |
| `k6_checks_rate` | gauge | `testid`, `check` |

```promql
# global p95 of create_order for one test
histogram_quantile(0.95, sum(increase(k6_http_req_duration_seconds{testid="load-20261002-160953", name="create_order"}[10m])))

# total requests
sum(increase(k6_http_reqs_total{testid="load-20261002-160953"}[10m]))

# VUs across all runners
sum(k6_vus{testid="load-20261002-160953"})
```

## Shop dashboard

Row **Load generator (k6, client side)**, filtered by the `k6 test` variable (`testid`):
VUs per runner, requests/s per request name, p95 seen by k6, failed requests and checks.

k6 p95 includes the network from the loadgen node; the service p95 rows below do not.
The gap between the two is time spent outside the services.
